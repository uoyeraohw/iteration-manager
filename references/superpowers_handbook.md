## 🔴 1. TDD 红绿重构铁律与测试反模式防御 (Test-Driven Development)

### 1.1 不可协商的第一铁律 (The Iron Law)
```text
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```
- **先写实现代码 = 违规重来**：如果你在看到失败的自动化测试之前就已经编写了生产业务代码，切勿将其保留为“参考”或边看边补测试——必须将其删除，严格从 Step 1 失败测试重新开始！
- **标准五步闭环**：
  1. **RED（编写最小失败测试）**：测试名清晰描述期望行为，每次仅测试一个具体行为，优先测试真实代码而非 Mock；
  2. **Verify RED（亲眼确认按预期失败）**：执行测试命令，确认测试是**因目标特性尚未实现而 FAIL**（绝不能是因为语法错误或拼写错误报错，更不能直接 PASS）；
  3. **GREEN（编写最小化实现代码）**：仅编写足以让当前测试通过的最简代码，严守 YAGNI，严禁顺手过度设计未测试的配置项；
  4. **Verify GREEN（确认全量绿灯）**：不仅当前新增测试必须 PASS，还必须运行项目级测试套件确认未破坏任何存量测试，且无异常警告；
  5. **REFACTOR（安全重构）**：仅在全绿状态下消除重复、提取辅助函数或优化命名，重构后再次验证全绿。

### 1.2 四大测试反模式红线 (Testing Anti-Patterns)
1. **反模式一：测试 Mock 行为而非真实业务行为**：严禁往 Mock 对象塞入预设返回值后再断言该 Mock 被调用——这只证明了测试框架没坏，未证明业务代码有效；
2. **反模式二：在生产类中混入仅测试使用的方法 (`Test-Only Methods`)**：测试辅助清理或构造逻辑必须放在测试工具模块中，严禁污染生产类接口；
3. **反模式三：在不理解依赖副作用时盲目 Mock**：Mock 前必须明确被隔离组件的真实契约与异常抛出形式；
4. **反模式四：事后补测合理化（"Tests after achieve the same spirit"）**：事后补写的测试受限于你写代码时记得的分支，从未经历 RED 阶段证明其能捕获缺陷。

## 🔍 2. 四阶段系统化根因排错纪律 (Systematic Debugging)

当测试出现非预期失败、构建报错或运行时异常时，遵循以下铁律：
```text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```
严禁凭直觉盲目猜改代码！必须严格按以下 4 个阶段推进：

### Phase 1: 根因调查 (Root Cause Investigation)
1. **完整精读报错堆栈与行号**：不跳过任何警告或错误码；
2. **稳定复现**：明确触发异常的确切命令与输入条件；
3. **检视近期变更 (`git diff`)**：排查当前任务或前置任务引入的接口/状态变化；
4. **多组件边界埋点追踪**：当数据流经多个模块（如 `API ➔ Service ➔ DB`）时，在边界处打印/断言入参与出参，定位第一个数据失真的节点。

### Phase 2: 模式比对分析 (Pattern Analysis)
1. 在现有代码库中寻找同类型的**正常可用实现**；
2. 逐项比对正常实现与故障实现的差异（调用顺序、上下文初始化、异步等待、类型转换）。

### Phase 3: 单一假设与最小探针验证 (Hypothesis & Testing)
1. 明确写出单一根因假设：*“我认为 X 是根因，因为 Y”*；
2. 每次**仅修改一个变量**进行验证；若假设被证伪，立即还原该改动，重新提出新假设，**绝对禁止把多个无效尝试叠加残留在代码中**！

### Phase 4: TDD 闭环修复与架构反思 (Implementation & 3-Strike Rule)
1. 定位根因后，先确保有复现该 Bug 的失败测试，再实施最小化根因修复（杜绝只屏蔽表象症状的 If-Else 补丁）；
2. **三次失败熔断法则（3-Strike Rule）**：如果连续 **3 次修复尝试** 均未解决问题，说明当前模块设计或计划假设存在结构性偏差——**立即停止第 4 次盲目尝试**，重新审视架构契约或记录 `Ruling:` 调整方案！

## 🛡️ 3. 完成前刚性实证门禁 (Verification Before Completion)

```text
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```
在将任务卡流转至 `🔵 待验收 (TESTING)` 或 `🟢 已完成 (DONE)` 前，必须通过五步门禁函数：
1. **IDENTIFY**：明确证明该验收项成立的客观终端命令；
2. **RUN**：实际执行验证并保留原始输出；同一候选及输入的有效证据可复用，不能凭历史印象、部分检查或Linter替代必要验证；
3. **READ**：完整阅读标准输出、错误输出与退出码（Exit Code 必须为 `0`，失败数必须为 `0`）；
4. **VERIFY**：逐条核对任务卡iter:acceptance 第6节的 `- [ ]` 验收复选框是否均已被客观输出证实；
5. **RECORD**：将实证命令与输出摘要如实填入任务卡iter:ledger 第7.1节。严禁出现“应该可以通过”、“看起来没问题”等主观措辞。

## ⚖️ 4. SDD 五轮修复循环、熔断器与偏差裁决协议 (Fix Loop & Rulings)

### 4.1 独立裁决而非停滞 (`Rulings, Not Stalls`)
在 `/iter next` 连续执行过程中，除以下 **4 类绝对红线** 外，不要在子任务之间暂停询问用户“是否继续”：
1. 不可逆的破坏性删除操作；
2. 高危安全/生产凭证变更；
3. 超出当前 Worktree 边界的外部副作用（如推送远程共享分支、发布包）；
4. 计划完全破损以至于所有前进路径均为盲猜。

遇到计划内部小冲突、接口命名笔误或边界未定义时，以迭代总目标为最高权威立即作出裁决，并在任务卡iter:ledger 第7.3节登记：
```text
Ruling: <你作出的具体决策> — <技术原因与依据> — <若该裁决有误时的修改代价>
```
**未记入任务卡iter:ledger 第7.3节账本的计划偏离属于严禁发生的“秘密篡改”。**

### 4.2 持久有界修复

按 [共同协议](agent_protocol.md) 记录稳定事件ID，默认单轮5、累计10、自动会诊1、自动重规划2，启动前可配置。重启和重复回收不清零；普通Ruling不是重规划。第3次连续失败先重新检验根因假设，不进行第4次盲修；完成根因分析后仍受总预算限制。

Critical/Important先核对正确性、契约与授权，再精准RED→GREEN；Minor记入Deferred Minors。第5次失败停止修复，在预算内会诊、重规划；先保存原始证据，不能自动采纳方案A或手工清零。累计/其它预算用尽保存FUSED/BLOCKED和具体恢复条件。会诊参与者不能独立审查本任务；Ruling不能把真实承重缺陷变成APPROVED或偷偷带入下一任务。
